The application form behind [Empresas en 24 Horas](/projects/e24h) has a legacy name inside the team: **VUF**. It started as a module inside the big government portal, a large chunk of TypeScript carrying the versions it had grown up on. A teammate pulled it out into its own repository. That was the easy part. The hard part was what it was still running: Next 13, React 18, Node 20, Tailwind 3, yarn.

I wanted all of it current. My honest estimate for a senior engineer doing this by hand, carefully, with QA between steps: **about two months**. It took **six and a half hours**, from the moment I created the plan to the last merged pull request. This post is about how, and about the things that broke, because those are the interesting part.

## What changed

| | Before | After |
|---|---|---|
| Next.js | 13 | 16 |
| React | 18 | 19 |
| Node (Dockerfile and CI) | 20 | 24 LTS |
| Package manager | yarn | pnpm |
| Tailwind CSS | 3 | 4 |
| Data fetching | react-query 3 | TanStack Query 5 |
| Headless UI | 1 | 2 |
| ESLint | 8 (`next lint`) | 9 (flat config) |
| PDF viewer | react-pdf 7 | react-pdf 11, with a download fallback |
| Browser tests | none | 13 Playwright tests, run in CI |

Five pull requests, about 80 files touched outside lockfiles. Most of the dependency tree moved to current, supported releases.

## The method: plan first, in the open

I did not start by asking an agent to "upgrade everything". That is how you get a 400-file diff nobody can review. I used [Matt Pocock's skills](https://github.com/mattpocock/skills), mostly three of them.

**`/wayfinder`** is the backbone. You hand it a foggy idea ("update our Next and related tooling") and instead of doing the work, it charts a **map**: a single GitHub issue with a destination, the decisions made so far, and a section called *Not yet specified* for the fog you can see coming but cannot phrase as a question yet. The map's children are **decision tickets**. Each one resolves a decision, not a slice of code.

**`/grilling`** is how the destination and the tickets get sharpened. It interviews you, in rounds, and for every question it proposes a recommended answer, worded so that "yes" accepts it. I come from Vue and Nuxt, and I told it so. When it asked whether to migrate to the App Router as part of this, I did not know the tradeoffs, so I said so, and it explained the options before asking again. At least once my whole answer was one word: *recomendados*.

**`/research`** handles the tickets that need facts. Each research ticket got its own agent, writing findings to a throwaway branch, reading primary sources instead of trusting memory.

The map ended up with eight decision tickets: which Node LTS, what Next 16 breaks in a Pages Router app, a compatibility matrix for every dependency, whether Tailwind 4 was worth it, how to move to pnpm, what a minimal Playwright suite should cover, an alternative to a PDF viewer with an absurdly high browser floor, and finally the order of the steps. Five of them were research tickets, and they ran in parallel and finished in about ten minutes.

The decisions that mattered came out of that stage, before any code existed:

- **Node 24, not 26.** Node 24 is the current LTS, and the PDF library needed a recent one anyway.
- **pnpm and Node move together,** because the new pnpm needs a newer Node than the one we had. So the first pull request does both.
- **Tests before upgrades.** Playwright goes in second, on the old stack, so every later step has a safety net that already passed once.
- **A jump straight to Next 16,** not 13 to 14 to 15 to 16. One set of breaking changes instead of three.
- **Tailwind 4 last and alone,** because it changes how the app looks, which no type checker can see.

The plan is the product here. When I later asked the agents to execute, there was nothing left to argue about.

## The execution: one ticket, one worktree, one builder

For execution I used a workflow I call `/horde`: one ticket, one git worktree, one builder agent. A separate orchestrator verifies, never trusts, and opens the pull request. Terminal sessions are managed with [herdr](https://herdr.dev), which keeps each builder in its own pane.

The rule I care most about: **a claim is not evidence.** Every time a builder said "done", the orchestrator re-ran typecheck, lint, build and the Playwright suite itself, built the Docker image, started it, and checked that it answered. Then two reviewers read the diff, one for architecture and one for security. If they found anything blocking, the findings went back to the builder, with a hard limit of three rounds. Only then did `/create-pr` open a pull request, ready for review, and I merged it.

## What the process caught

This is the part that would have hurt in production.

- **The container image broke the first time it was really built.** Local builds passed; the first real image build did not. A copy step was dragging files from my machine into the image and overwriting the container's own.
- **Next 16 changed a server default.** The container started, but its health check could not connect. A reviewer predicted it from reading the code, and a real container confirmed it.
- **CI used a different build mode than my machine.** Next 13 shrugged at the difference. Next 16 crashes while prerendering the 404 page. Our local builds used the default, so nothing reproduced it. CI caught it.
- **A new browser test failed now and then under load.** It looked like a flaky test. It was a real bug: Tailwind 4 removed the `transform` class, which in v3 quietly kept the modal panel above its dark backdrop. Without it, the backdrop could swallow clicks on the modal's own buttons. It only showed up under load. The fix was one word, `relative`. Before it, the test failed 15 to 31 times in 80 runs under load; after it, 80 of 80 passed.
- **An error boundary that never caught anything.** It looked right in the diff and passed its own tests. A reviewer noticed it kept no state, so in React 19 a render error would unmount the whole app instead of showing the fallback.
- **Tailwind 4 changes defaults that compile fine.** Reviewers measured the compiled CSS in a real browser and found date inputs two pixels shorter, a white focus ring where there used to be a blue one, buttons that lost their pointer cursor, and darker placeholders. A pixel diff of ten key screens against the old build showed zero difference in nine, and about 0.03 percent in the tenth.
- **A dependency guard got bypassed.** A builder skipped a safety check on brand-new releases to install a package published hours earlier. The review sent it back; an older version did the job.

Anything that was not part of the upgrade went to the issue tracker instead of getting fixed in passing. A migration pull request should be about the migration.

## The honest limits

I would not call it magic.

- **The agents were not right the first time.** Almost every ticket needed at least one round of review fixes. The process worked because it assumed that.
- **The tests are a net, not a guarantee.** Thirteen Playwright tests with a fully mocked API cover the redirect, the form, an upload, saving, the request detail page, the PDF viewer and the 404. They are a net for the main flows, not for everything.
- **The PDF viewer got worse for older browsers.** The current version of its engine needs very new browser APIs, so many people will get a "download the PDF" fallback instead of the viewer. We accepted that on purpose in exchange for staying on a maintained library. It deserves a real-world check.
- **The expensive part is still mine.** A full manual regression, on real browsers and devices. No agent replaces that.
- **It is not free.** By the end of the day my weekly AI usage meter was at 96 percent.

## What I would tell you to steal

1. **Make the plan an artifact on your issue tracker,** with decisions recorded as they are made. It survives the end of a session, and a new agent can pick it up cold.
2. **Spend the first hour on questions, not code.** Everything above that went smoothly went smoothly because it was decided in the first hour.
3. **Put the safety net in before the change it protects.**
4. **Separate the thing that writes from the thing that verifies.**
5. **Keep the risky, visible change alone.** Tailwind got its own pull request because of what it does to pixels.

Two months became an afternoon, and I still would not merge any of it without the humans-in-the-loop part. Both of those are true at the same time.
